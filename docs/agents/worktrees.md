# Агент в worktree

Правилата за агент, който имплементира билет в собствен git worktree (напр. implementer подагент на `/implement-spec`). Briefing-ът дава само билета, клона и интеграционния клон; останалото е тук.

## Начало

- Worktree-ът е в `../family-worktrees/<име>` на собствен клон. Провери, че съдържа върха на интеграционния клон (`git merge-base --is-ancestor <интеграционен> HEAD`); ако не, `git reset --hard <интеграционен>`. После `pnpm install`.
- Прочети документите от `AGENTS.md` → Project docs и бележките на предишните билети, ако briefing-ът сочи към тях.

## Среда

- **Тестова база:** `docker compose -p family-test --profile test up -d postgres-test`, ако портът 127.0.0.1:5433 не е зает; ако е, сървърът вече работи и се ползва както е. Всяко копие на repo-то получава своя база на този сървър автоматично ([testing.md](../testing.md) → Механика), затова `pnpm test` върви без допълнителни env променливи.
- **Чужди контейнери и compose проекти** остават недокоснати. Локален стек за ръчна проверка се пуска с отделно име на проект: `docker compose -p family-<билет> …`.
- **Сървър, който пуснеш** (`pnpm dev`, `tsx watch`, Vite), спираш сам, заедно с родителския процес. Преди отчета `ss -tln` показва свободни 18090, 18091 и 5173: оркестраторът не може да убива процеси в тази среда.
- **Ръчните стъпки на човека** (smoke срещу `homesrv`, реалният агент, Provisioning, проверка на телефон) остават за него: подготви скрипта и командата, без ssh към сървъра.

## Край

- `pnpm lint && pnpm typecheck && pnpm test` са зелени.
- Commit-ите са conventional (`feat(<обхват>): … (#<билет>)`).
- Merge на върха на интеграционния клон в твоя клон; при нови commit-и тестовете минават пак.
- Push, merge в интеграционния клон и затваряне на issues прави оркестраторът.
- Отчетът: commit-ите, какво е направено, отклоненията от билета с причина, бележки за следващия билет.
